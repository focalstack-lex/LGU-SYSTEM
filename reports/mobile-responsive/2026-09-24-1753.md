# Mobile Responsiveness Audit — COE LGU System

**Date:** 2026-09-24 17:53
**Scope:** `client/` (7 pages, 6 stylesheets, ~15k lines JS), `electron/`, `client/manifest.json`, `client/sw.js`
**Status:** AUDIT ONLY — no fixes applied, per instruction.
**Verdict:** Strong mobile foundation with a small number of sharp, verified breaks. Not a rewrite; the gaps cluster in **one specific width band (481–768px)** and in **two non-portal pages**.

---

## 1. Method

Three independent passes, so findings are evidence-backed rather than inferred:

| Pass | What it did |
|---|---|
| Static CSS/HTML/JS analysis | 4 parallel deep-reads of `main.css`, `officer.css`+`ai.css`, all 7 HTML pages, all `client/js/**` + Electron/PWA config |
| Live rendered measurement | `scripts/audit-mobile-responsive.mjs` — Playwright/Chromium across 8 viewports × 7 pages, measuring clipped overflow, sub-16px inputs, sub-44px targets |
| Targeted claim verification | `scripts/verify-mobile-claims.mjs`, `verify-mobile-claims2.mjs` — computed-style checks for each specific CSS claim |

**Critical measurement note:** `html`/`body` set `overflow-x: hidden` (`main.css:271-272`, `295`), so horizontal overflow is **clipped, not scrollable** — `documentElement.scrollWidth` cannot detect it. The harness therefore compares element bounding rects against the viewport, and flags whether a scrollable ancestor exists (intentional scroll region) versus clipped content (bug).

Screenshots: `reports/mobile-responsive/shots/`

## 2. Headline

The system is **much more mobile-ready than a typical app at this stage**, and it is important not to "fix" what already works:

- All three portal pages carry a full viewport meta (`viewport-fit=cover`, `interactive-widget=resizes-content`) `[STATIC]`
- Both portals have **complete mobile nav parity** — a bottom nav plus a "More" sheet containing every sidebar destination. Every desktop destination is reachable on a phone. This is why there is **no P0 navigation gap**. `[STATIC]`
- `env(safe-area-inset-*)` is used in 26 places, and **every page that calls `env()` also has `viewport-fit=cover`** — so insets never silently resolve to 0. `[STATIC, verified by cross-grep]`
- Modals are correctly clamped (`max-height: calc(100dvh - 2rem)`, `overflow-y: auto`)
- Student financial tables already swap to cards on phones; grids collapse; the auth screen flips to a column with safe-area padding
- `touch-action: manipulation`, passive scroll listeners, `prefers-reduced-motion`, and pointer/touch long-press handling for stat cards are all implemented

The real defects are narrower and specific — described below.

## 3. Findings

### P0 — 481–768px: the ledger/income/reports cards render completely unstyled while the table is hidden `[VERIFIED]`

This is the single most impactful defect. Between 481px and 768px — **landscape phones, small tablets, and iPad Mini portrait** — the app hides the data table and shows the mobile card layout, but the card CSS lives only in the ≤480px block.

- The card container is revealed at ≤768px — `styles/main.css:3627-3638` (inside the `@media (max-width: 768px)` block opened at `3533`), while the table is hidden at `3621-3625`
- Every `.data-card*` rule lives inside the `@media (max-width: 480px)` block opened at `3729` — `styles/main.css:3903-3932`

Measured on `/` with a card injected into the real container:

| Property | 400px | **600px** |
|---|---|---|
| `#tx-mobile-cards` display | `flex` | `flex` |
| `.table-wrapper` display | `none` | `none` |
| `.data-card` background | `rgb(28,28,32)` | **`rgba(0,0,0,0)`** |
| `.data-card` border / radius / padding | `1px` / `12px` / `13.6px` | **`0px` / `0px` / `0px`** |
| `.data-card-row` | `flex`, `space-between` | **`block`, `normal`** |

**Impact:** on a tablet or a phone in landscape, the student's transaction ledger, income list, and report breakdown lose their card surface, padding, and label/value row layout entirely; per-row action buttons lose their container styling. Data remains legible as running text, but the designed layout is 100% absent. Applies to `#tx-mobile-cards`, `#income-mobile-cards`, and the reports containers.

### P1 — Onboarding modal inputs are 13.6px and defeat the 16px guard at *every* width `[VERIFIED]`

`styles/main.css:1532` (and `1613-1619`):

```css
.onboarding-card .form-group input,
.onboarding-card .form-group select,
.onboarding-card .dd-trigger {
  font-size: 0.85rem !important;   /* 13.6px */
}
```

Specificity `(0,2,1)` + `!important` beats the global guard `input, select, textarea { font-size: 16px }` (`264-269`, specificity `(0,0,2)`) **and** the mobile hard override `body input, body select, body textarea { font-size: 16px !important }` (`3935`). Measured: **13.6px at 768px, 13.76px at 390px** — the only inputs in the student portal that survive the guard.

**Impact:** the first-run onboarding gate (`index.html:112`) is the first thing a new student touches. Focusing any field makes iOS Safari zoom to ~1.3× and the modal visually breaks. Same class of bug in the profile modal at 481–600px (`.profile-modal … font-size: 0.84rem`, `main.css:6273`) and `.enrollment-filter-select` at 13.1px (`main.css:8107`).

### P1 — `ai.css` has no rules at all for 641–768px `[VERIFIED]`

`ai.css` has exactly two breakpoints: `@media (min-width: 769px)` (`ai.css:30`) and `@media (max-width: 640px)` (`ai.css:1211`). **641–768px matches neither.**

Measured launcher position on `/`:

| Viewport | launcher `bottom` | launcher `right` | `.ursa-launcher-text` |
|---|---|---|---|
| 390px | 72px | 13.6px | `none` (compact) |
| 500px | 72px | 13.6px | `none` |
| **641px** | **74px** | **20px** | **`flex`** (full labelled pill) |
| **700px** | **74px** | **20px** | **`flex`** |
| 769px | 32px | 32px | `flex` |

In the 641–768px band the launcher sits at the base `bottom: calc(74px + env(safe-area-inset-bottom))` (`ai.css:9`) — an offset whose stated purpose is to clear the floating bottom nav — while `.bottom-nav` is `display: none` at that width (it is only revealed inside the ≤480px block, `main.css:4096`). So the FAB floats 74px above the corner with a dead 74px gap beneath it, and never gets the desktop `2rem` positioning. The AI drawer likewise keeps `width: 440px; max-width: 92vw` (`ai.css:151-153`) and never reaches the full-width `≤640px` treatment.

**Impact:** layout inconsistency, not a functional break — the same 72–74px orphaned offset also affects 481–640px, where the bottom nav likewise does not exist.

| Element | font-size |

### P1 — Officer KPI popovers are clipped by the card's own `overflow: hidden` `[CSS-SPEC]`

`styles/officer.css:240-253`:

```css
.of-stat { position: relative; overflow: hidden; }
.of-stat .stat-popover { position: absolute; top: calc(100% + 8px); }   /* 331-353 */
```

The popover is a direct child of `.of-stat` (`js/officer/officer-app.js:807-844`), so `.of-stat` is both its containing block and its clipper — and it is positioned 8px *below* that block. It is therefore always clipped away. Nothing resets `overflow` when it opens: `.of-stat.hover-active` (`362-367`) only changes `border-color`/`z-index`.

**Impact:** on mobile this is the **only** way to read the breakdown of Available Cash / Total Income / per-event allocations (via the long-press handler at `officer-app.js:939-945`), and on desktop it breaks hover. Contradicts the working model in `main.css:2473-2497`, where `.stat-card` correctly has no `overflow: hidden`. Not runtime-confirmed (needs auth), but clipped-by-specification is deterministic.

### P2 — Long unbreakable tokens are clipped with no recovery path `[VERIFIED]`

`overflow-wrap`, `word-break`, and `hyphens` appear **zero times** across all six stylesheets. Combined with `overflow-x: hidden` on `html`/`body` (`main.css:271-272`, `295`) and `.of-main` (`officer.css:113`, `1614`), any unbreakable token — a long CJC GSuite email, a reference number, a URL — is cut off at the viewport edge with **no scroll and no ellipsis to reveal it**. Exposed text: `.announce-body.expanded` (`main.css:2942-2957`), `.faculty-app .mono` (`8684-8689`, `nowrap`), `.ev-status-meta` (`8515`), `.of-announce-item p` (`officer.css:1362`), `.of-alert-item` (`1277`), `.ursa-bubble` (`ai.css:434`). Some places do handle it deliberately with `text-overflow: ellipsis` (`main.css:776, 1845, 2762, 2887, 5123, 6031, 7205, 7996, 8126`).

### P2 — Officer data tables scroll but have no mobile card alternative `[STATIC]`

All four tables are wrapped in `.of-table-wrap { overflow-x: auto }` (`officer.css:776-783`), so nothing overflows the page — but `.of-table th { white-space: nowrap }` (`846`) and `.num { white-space: nowrap }` (`890`) mean the 6-column People table (`officer.html:421-431`) is always wider than a phone. There is no card-collapse (student portal has one), no scroll hint, and no `position: sticky` first column — so the row identity scrolls off-screen while the user reaches the "Change Role" control at the far edge. `min-width: 580px` on the curriculum table (`2085`) is the same story.

### P2 — Unguarded `100vh` / fixed heights `[STATIC]`

- `.of-gate { min-height: 100vh }` (`officer.css:1417`) — renders on phones, over-reports the visible viewport under iOS's dynamic toolbar. `main.css:290-291` and `ai.css:154-155` do this correctly with a `dvh` fallback.
- `.of-sidebar { height: 100vh }` (`officer.css:33`)
- `main.css:6586-6589` declares `max-height: calc(100dvh - 1.5rem) !important` and then `calc(100vh - 1.5rem) !important` on the next line — the `vh` value wins and defeats the `dvh` intent.
- `ai.css:857-859` fixes the prompt grid at 212px tall, with no `dvh` variant for short landscape.

### P2 — 320px: `.events-grid` minimum track overflows `[STATIC]`

`main.css:3027` `grid-template-columns: repeat(auto-fill, minmax(300px, 1fr))` with no narrowing override. At 320px the content box is ~296px, so the track overflows by ~4px and is silently clipped by `overflow-x: hidden`. Measured page-level overflow was 0 at 320px (clipping hid it), so this is a small latent defect.

### P2 — Faculty toast can overflow below ~380px `[STATIC, latent]`

`.faculty-toast { max-width: 360px }` (`main.css:8807-8817`) anchored `right: 1.25rem` (`8798`) needs ~380px. At 320px it extends past the left edge. No media override anywhere. Not reproduced in measurement because the toast requires an interaction to appear.

### P3 — Structural & hygiene

- **Stray `}` in `main.css:7679`** — invalid CSS, brace count 1348 `{` / 1349 `}`. Verified visually harmless, but unsafe for future edits. (The `officer.css` equivalent at `1814`/`1846` is *not* harmless — see P1.)
- **`.onboarding-grid-row` never collapses** — `grid-template-columns: 1fr 1fr` at both `390px` and `768px` `[VERIFIED]` (`main.css:1540-1544`, re-declared `1621-1625`). At 320px each column is ~128px.
- **Inconsistent breakpoint set** — 340 / 380 / 480 / 600 / 640 / 768 / 900 / 1024 / 1023.98 + `min-width` 640 / 769 / 1024. Some are deliberate, but the set is wide enough that the 641–768 (P1) and 481–768 (P0) gaps went unnoticed. Also: **the two portals use different nav breakpoints** — officer switches to mobile shell at ≤900px (`officer.css:1504`), student only reveals its bottom nav at ≤480px (`main.css:4096`). A 600px-wide device therefore gets a bottom-nav pill in one portal and a 60px icon rail in the other.
- **Dead rule:** `.mobile-profile-btn { display: flex }` at ≤640px (`main.css:5875-5879`) is inside `.app-mobile-header`, which is `display: none` above 480px (`main.css:3517-3520`) `[VERIFIED: display=none at 481/600/768]`. The 481–640 branch can never render — this was presumably the intended fix for the P1 account-pill bug, wired to the wrong container.
- **Touch targets under 44px** `[VERIFIED]` — measured 4 on the app shell at both 390px and 320px: `.app-mobile-brand` (151×37), two `.btn-icon` (36×36: theme + logout), `.grizz-launcher` (42×42). Also `[STATIC]`: `.unit-action-btn` 26×24 (`main.css:5439`) — edit/pass/delete on mobile are ~half the guideline and packed at `gap: 1px`; `.receipt-viewer-btn` 36×36 (`7215`); `.events-filter-btn` ~34px (`3091`); `.of-page-btn` 30px (`officer.css:957`); `.of-modal-close` 34px (`1027`); `.of-check-input` 17px (`859`); `.ursa-tab-btn` ~30px (`ai.css:791`).
- **No `inputmode`/`enterkeyhint` on money fields** `[STATIC]` — 8 peso fields use `type="number"` with no `inputmode="decimal"` (e.g. `index.html:558,771,814,916,975`; `officer.html:196,258,278`), so iOS's number pad offers no decimal separator for centavo entry. `cv-builder.html:132` already demonstrates the fix pattern in this codebase.
- **Missing `autocomplete`** on auth/profile fields `[STATIC]` — `index.html:84,90,195,1515,1579`, `officer.html:1056,1120,1125`. No `autocomplete="username"` / `"current-password"` / `"new-password"`.
- **`role="button"` divs instead of `<button>`** `[STATIC]` — 9 instances (`index.html:255,316,351,367,379,391,1463`; `officer.html:49,109,1004`); 4 carry only `title`, not `aria-label`. Icon-only close buttons in `officer.html:783,836,211` lack `aria-label`, while the student-portal equivalents have one.
- **Unassociated `<label>`s** on money forms `[STATIC]` — `index.html:557,770,813,916,975,1040` and `officer.html:185,196,257,278` lack `for`, so tapping the label does not focus the field.
- **Service worker app-shell is incomplete** `[STATIC]` — `client/sw.js:15-51` omits `receipt-modal.js`, `roster.js`, `grizz-recommend.js`, `enrollment.js`, `enrollment-journey.js`, `officer/curriculum.js`, and `faculty.html` / `cv-builder.html`. Asset fetches are network-first, so an offline installed PWA fails to load those modules.
- **Manifest `start_url` always opens the student portal** (`manifest.json:6`) — an officer who installs from `officer.html` (which links the same manifest, `officer.html:10`) lands in the student portal. `scope`/`display`/maskable icons are otherwise correct.
- **Viewport meta inconsistencies** — none cause a live bug, but for the record: `cv-verify.html:5`, `feedback/index.html:5`, `feedback/view/index.html:5` use a bare `width=device-width, initial-scale=1.0`. This is **safe** because those pages call no `env()`. `cv-builder.html:5` has `viewport-fit=cover` but no `interactive-widget`, and it is the most form-heavy page — on Android Chrome the soft keyboard overlays the editor instead of resizing it.
- **Faculty topbar ignores the top inset** `[STATIC]` — `faculty.html:14` opts into `black-translucent` standalone mode, but `.faculty-topbar { padding: 1.1rem clamp(...) }` (`main.css:8661-8665`) has no `env(safe-area-inset-top)`. The other two portals do add it (`main.css:3943`, `officer.css:1523`). Launched from the home screen, the logo and title collide with the status bar/notch.
- **Resize handling** `[STATIC]` — `window.innerWidth <= 768` is used as a *touch test* in `js/dashboard.js:156`, so shrinking a desktop window to ≤768px swallows the first click on a stat card. `js/reports.js:264` (≤640) and `js/enrollment.js:455` (≤480) read media state once at render with no change listener, so rotating does not re-apply. No `orientationchange` listener exists anywhere. Stat-card popovers are clamped only when opened (`dashboard.js:33-48`, `officer-app.js:899-910`), so rotating with one open leaves it off-screen.
- **Needs device confirmation (not verified):** `body.modal-open { touch-action: none }` (`main.css:299-302`) is set on `body` and intersected with all descendants; tall modals rely on `.modal-card { overflow-y: auto }`. Whether this actually blocks finger-scrolling inside modals on iOS Safari / Android Chrome needs a real device. The AI drawer also has no body scroll lock (`ai-assistant.js:293-309`), so at >640px the exposed page sliver can scroll behind it.

## 5. Proposed fix sequence (for approval — nothing applied)

Ordered by impact per unit of risk. All are additive CSS/attribute changes; no API, schema, or route changes are required, per `AGENTS.md` §3.

1. **Fix the `officer.css` brace** (`1814`/`1846`) — one line, restores desktop forms and filter bars. Highest value, lowest risk.
2. **Move `.data-card*` out of the ≤480px block** into ≤768px (or to base) — resolves P0 for tablets and landscape phones.
3. **Reflow the sidebar footer for the 60px rail** at 481–768px, or reveal the mobile header/bottom nav from ≤768px instead of ≤480px — resolves the off-screen account pill and incidentally unifies the two portals' nav breakpoints.
4. **Raise onboarding/profile/feedback input font-size to ≥16px** and drop the `!important` — kills all iOS focus-zoom, three sites.
5. **Add a `max-width: 768px` block to `ai.css`** (or change `ai.css:30` to `min-width: 769px` → `641px`) — closes the dead zone.
6. **Add `.of-stat { overflow: visible }`** on popover open — restores mobile KPI breakdowns.
7. **Add `overflow-wrap: anywhere`** to the long-text selectors listed in P2, and `inputmode="decimal"`/`autocomplete` attributes.
8. Hygiene: stray `}` in `main.css:7679`, dead `.mobile-profile-btn` rule, `.onboarding-grid-row` collapse, sub-44px touch targets, `dvh` fallbacks, SW app-shell list, manifest `start_url`.

**Suggested verification for each:** extend `scripts/audit-mobile-responsive.mjs` into a regression gate asserting `overflowCount === 0` and `zoomInputs.length === 0` at 320/390/600/768/844-landscape, then re-run.

## 6. Reproduce

```bash
npm start                                   # server on :3000
node scripts/audit-mobile-responsive.mjs    # full viewport sweep -> reports/mobile-responsive/
node scripts/verify-mobile-claims.mjs       # nav/account, officer.css leak, ai.css zone, feedback fonts
```

All three harnesses are read-only (they load pages and read computed styles; they never submit a form or write data). The `student-portal (app shell forced)` rows in the sweep force `#app-screen` visible to measure the authenticated shell without credentials — layout boxes and CSS are real, but **content-dependent findings (e.g. P0) were confirmed by injecting a card into the real container**, not inferred from the forced-empty shell.
