## iPhone bottom band, fourth pass: the nudge now really scrolls (branch: ui/nav-consolidation)

- [01:03] The recording proved that a real document scroll is what makes iOS recompute the stale standalone viewport. `kickViewportRelayout` in `ui.js` only changed the body height and dispatched a synthetic resize event, which WebKit ignores. ## iPhone bottom band, fifth pass: structural cause, translucent status bar (branch: ui/nav-consolidation)

- [01:10] The user reports the band persists on the new build. Re-measured the recording frames: the unpainted strip is about 49pt tall and the nav sits about 85pt above the screen edge; the iPhone 11 status bar is 48pt and the home-indicator inset 34pt. So on a cold standalone launch iOS sizes the web view short by the status bar height (as if it did not extend under the bar) while still reporting the bottom inset, and only a user touch scroll makes it recompute. That is the `apple-mobile-web-app-status-bar-style=black-translucent` behaviour; programmatic scrolls do not trigger the frame update, which is why passes two to four could not help. Fix: the three installable pages (`index.html`, `officer.html`, `faculty.html`) now declare `black` (opaque). The view frame no longer depends on the translucent computation, `env(safe-area-inset-top)` resolves to 0 and the mobile headers (which pad with it) shrink gracefully; the cost is a solid black status bar above the charcoal header. Documented in `UI_DESIGN.md` Safe Area Insets. The dvh shell, `--vvh` sync and scroll nudges stay as defence in depth.

## Verified accounts sent back to the enrollment gate (branch: ui/nav-consolidation)

- [01:23] Reported: an account already verified by an officer lands on "Enrollment Verification Required" after the PWA reinstall. Root cause in `app.js` (student gate at login): it never read `profiles.is_verified`, the flag the server sets when an officer verifies an account (`POST /api/admin/users/:id/verify`) or approves a request. It trusted only two direct Supabase lookups: a name-token match against `enrolled_students` and an approved row in `enrollment_verification_requests`, the latter served first from a localStorage cache that the reinstall wiped. An account verified from the Accounts tab has neither a roster row nor a request row, so it was gated for good. Second defect in `roster.js`: the page-load pre-fetch runs before a session exists and resolves to an empty list; a login check that arrived while that promise was pending shared it and matched against nothing. Fix: the gate is skipped when `profile.is_verified === true` (server-authoritative; roster and request lookups remain for legacy accounts), and `getRoster()` re-fetches when the shared promise came back empty and a session is now available. Cache-busters: app.js 6.9, roster.js 5.6 on both pages. New `scripts/verify-verification-gate.mjs` drives three cases with the mocked backend (verified profile with empty roster and no request must enter; unverified with nothing must be gated; unverified with a roster match must enter); it fails case A on the old code and passes 3/3 on the fix.
